A credit-default prediction system on the Home Credit dataset: given an applicant's
data plus their credit-bureau history, predict whether they default, and turn that
into an approve/decline decision. Built as a portfolio piece for end-of-studies
interviews, so the point isn't a leaderboard score, it's the parts a notebook usually
skips: point-in-time feature construction across a multi-table join, a validation
scheme that doesn't cheat on time, calibrated probabilities, a threshold picked from
an actual cost matrix instead of 0.5, and the whole thing served behind a real API
instead of sitting in a notebook cell.

## Data

Home Credit Default Risk, from Kaggle: https://www.kaggle.com/c/home-credit-default-risk

```
kaggle competitions download -c home-credit-default-risk
unzip home-credit-default-risk.zip -d data/
```

`data/` is gitignored. Nothing in this repo depends on the raw CSVs being present
except training (`train_final_model.py` and the walk-forward scripts) -- the served
API only needs the trained artifacts, not the dataset.

## Architecture

```
src/
  splits.py             walk-forward split (component 2)
  check_integrity.py    row counts, key coverage, schema sanity (component 1)
  baseline.py           application_train only, no joins (component 3)
  bureau_features.py    point-in-time bureau.csv aggregation (component 4)
  with_bureau.py        joins bureau features onto application, shared dataset builder
  train_eval.py         shared walk-forward train/eval loop
  calibration.py        isotonic calibration (component 5)
  threshold.py          cost-based threshold sweep (component 6)
  train_final_model.py  trains + persists model.pkl / calibrator.pkl / manifest.pkl
  serve.py              FastAPI serving layer (component 7)
tests/
  test_bureau_leakage.py   point-in-time filter + missing-not-zero guards
  test_api.py              /health, /predict contract, no-bureau-history path
artifacts/               generated by train_final_model.py, gitignored
DECISIONS.md              what/why/rejected-alternative for every modeling choice
```

Each `src/` module is runnable on its own (`python <module>.py` from inside `src/`)
and prints its own report. Nothing here is a notebook; every number in this README
came from one of these scripts.

## Headline results

| model | PR-AUC | lift@10 | lift@20 |
|---|---|---|---|
| baseline (application only) | 0.237 | 3.24 | 2.56 |
| + bureau features | 0.246 | 3.33 | 2.61 |

PR-AUC (average precision) is the headline metric, not accuracy or plain ROC-AUC,
because the base rate is ~8% positive. Both numbers are the mean over 4 walk-forward
folds; the holdout was never touched to produce them.

At the chosen cost-based threshold (0.1225, from a 7.5:1 loss-given-default to margin
cost ratio), expected cost drops **21.8%** versus using a plain 0.5 threshold, and
25.2% versus approving everyone.

## Design highlights

**Point-in-time correctness, with a test to prove it.** Every bureau feature is
computed only from rows where `DAYS_CREDIT < 0 AND DAYS_CREDIT_UPDATE < 0` -- the
credit itself predates the application, and the bureau's last status refresh on that
credit does too. Verified empirically, not assumed: among rows passing both cutoffs,
the actual closure date never lands on or after the application. Five pytest cases in
`test_bureau_leakage.py` pin this down, including the case where an applicant's entire
bureau history fails the filter (falls back to NaN, not zero) and the case where a
naive `.sum()` would silently turn an all-missing field into a fake zero.

**Walk-forward split, checked against drift rather than trusted blindly.** This
dataset has no real calendar date, only per-applicant relative day offsets, so
`SK_ID_CURR` ascending order is used as a time proxy: a final holdout carved off the
end, and expanding-window walk-forward blocks for everything before it. A PSI check
on 7 representative features between the earliest and latest blocks came back flat
(0.0002-0.0007, far under the "no shift" threshold) -- which says the split cost
nothing relative to random here, not that the discipline is optional. The walk-forward
scheme applies regardless of what PSI shows, because PSI on observed features can't
see label drift.

**Isotonic calibration, with the tradeoff reported instead of hidden.** Isotonic
regression pulled the reliability curve's mean gap from 0.0031 to 0.0000, but it also
pooled 52,220 of 52,276 raw scores into just 56 distinct calibrated values. ROC-AUC
and both lift metrics held up or improved slightly; PR-AUC dropped 1.9% from that
coarser resolution. Reported both, with the reasoning for why one metric moved and the
others didn't, rather than only showing the flattering numbers.

**Cost-based threshold, not 0.5.** The decision threshold comes from an explicit,
jointly-agreed cost matrix (loss-given-default at 75% of principal vs. 10% margin
foregone on a wrongly-declined applicant, a 7.5:1 ratio), swept empirically against
realized outcomes and cross-checked against the closed-form optimum. The tie-break
rule at the cutoff (thousands of applicants share the same calibrated score after
isotonic pooling) is stated explicitly: ties decline, since that's the cheaper error
given the cost asymmetry.

**One implementation of "what a bureau feature is."** The serving API accepts raw
bureau tradelines, not pre-computed aggregates, and calls the exact same
`filter_point_in_time()` / `aggregate_bureau()` functions training used. No second
implementation to drift out of sync with the leakage-tested one.

## Live example

```
POST /predict
{
  "application": { "AMT_INCOME_TOTAL": 180000, "AMT_CREDIT": 900000, "...": "~120 fields total, unset ones default to null -> NaN" },
  "bureau_records": [
    { "DAYS_CREDIT": -1740, "DAYS_CREDIT_UPDATE": -8, "CREDIT_ACTIVE": "Closed", "CREDIT_TYPE": "Consumer credit", "AMT_CREDIT_SUM": 45000, "...": "..." }
  ]
}
```

Response, for a real applicant from the dataset (116 real bureau tradelines, actual
outcome: did not default):

```json
{"probability": 0.07060255629945221, "decision": "approve", "threshold": 0.1225}
```

Same applicant with `"bureau_records": []` (no bureau history):

```json
{"probability": 0.06296296296296296, "decision": "approve", "threshold": 0.1225}
```

## Limitations / what I'd do next

- **ID-order as a time proxy is unverified, not proven.** `SK_ID_CURR` ascending order
  is the only ordering signal in this dataset, and there's no documentation tying it
  to real application chronology. The PSI check didn't find drift, but that's weak
  evidence at best -- it can't see label drift or a shifted feature-target relationship.
- **Behavioral tables are deferred.** `previous_application`, `POS_CASH_balance`,
  `installments_payments`, `credit_card_balance`, and `bureau_balance` aren't in the
  model. Each would need the same point-in-time treatment bureau.csv got, and each is
  a bigger table with more join complexity; only worth adding if it beats the current
  PR-AUC by enough to justify the added leakage surface.
- **Single model, no ensembling, no hyperparameter search.** LightGBM with
  conventional defaults throughout. Tuning was deliberately deferred so that
  "did this table help" comparisons weren't conflated with "did retuning help,"
  not because the model is presumed complete -- these numbers aren't comparable
  to a tuned production model.
- **Calibration and threshold selection both lean on the same validation block**
  (block_4), for lack of a dedicated calibration split -- it's doing early-stopping,
  calibration-fitting, and calibration-evaluation duty at once. The holdout is the only
  place this gets a genuinely out-of-sample check, and that hasn't happened yet: it's
  meant to be touched exactly once, at the very end.
- **The cost matrix (75% LGD, 10% margin) is a stated assumption, not derived from
  this data.** There's no recovery or interest-rate data in this dataset to fit those
  numbers directly; the sensitivity table in DECISIONS.md shows how much the threshold
  moves if they're wrong.
- **No auth, no persistence layer on the API.** Deliberately out of scope for what
  this is meant to demonstrate; would be a prerequisite for anything beyond a demo.

## Quickstart

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# data/ populated per the Data section above

cd src
python check_integrity.py       # schema/key sanity
python splits.py                # walk-forward split + PSI report
python baseline.py               # application-only baseline
python with_bureau.py            # + bureau features
python calibration.py            # isotonic calibration report
python threshold.py              # cost-based threshold selection
python train_final_model.py      # persists artifacts/ for serving

cd ..
pytest                            # 11 tests: leakage guards + API contract

# run the API directly
cd src && uvicorn serve:app --reload

# or via Docker (needs artifacts/ already trained, see above)
docker compose up --build
```

`/health` and `/predict` are documented at `/docs` once the service is running
(FastAPI's autogenerated OpenAPI UI).
